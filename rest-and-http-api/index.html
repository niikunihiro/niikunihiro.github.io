REST と HTTP API の違い：統一インターフェースの誤解

  • July 02, 2025
  • 2307 words
  • 12 min

“REST API” という言葉はソフトウェア開発の現場で頻繁に使われています。しかし、「REST とは何か？」と問われると、意外とはっきり答えられないことがあります。「GET や POST を使っているから REST でしょ？」という感覚で使われていることも多いのではないでしょうか。

この文書では、REST と HTTP API の違いを丁寧にひもときながら、その誤解を整理し、実際の API 設計に役立つ考え方へとつなげていきます。

読み終える頃には、“REST API” と HTTP API の違いを説明できるようになり、今後の API 設計において、より良い判断ができるようになるはずです。

REST と HTTP API のよくある誤解

多くの開発者が “REST API” と呼んでいるものは、実際には HTTP メソッド（GET, POST, PUT, DELETE など）を使ってデータの CRUD 操作を行っている API です。

確かにこれは「HTTP を使った API」ではありますが、REST の設計原則に基づいているかというと、必ずしもそうとは言えません。Roy Fielding が 2000 年に提唱した REST は、単なる技術の使い方ではなく、Web システム全体のアーキテクチャスタイルです。

HTTP を使っているから REST、というわけではないのです。

REST とは何か

REST（Representational State Transfer）は、分散システム、特に Web における効率的で拡張可能なアーキテクチャを実現するための設計原則です。以下の 6 つの制約から構成されています：

  1. クライアント・サーバーの分離
  2. ステートレス性
  3. キャッシュ可能性
  4. 統一インターフェース（これが REST の中核）
  5. 階層化システム
  6. コードオンデマンド（任意）

この中でも特に混乱が多いのが「統一インターフェース」です。この要素に焦点を当ててみましょう。

統一インターフェースの本当の意味

統一インターフェース（Uniform Interface）は、REST アーキテクチャの中核的な制約です。

多くの人は、「GET で取得、POST で作成、PUT で更新、DELETE で削除」のような操作が揃っていれば REST だと考えがちですが、それは統一インターフェースのごく一部に過ぎません。

統一インターフェースには、次の 4 つの要素が含まれています：

1. リソースの識別

すべてのリソースは URI によって一意に識別される必要があります。たとえば、/users/123 は「ID が 123 のユーザー」というリソースを指します。リソースとはデータの単なる集合ではなく、意味を持った“対象”であることが重要です。

2. リソースの操作は表現を通して行う

クライアントはリソースの本体に直接アクセスするのではなく、リソースの 表現（representation） を通じて操作を行います。たとえば JSON 形式のユーザー情報を取得して表示したり、編集して送信したりするのがこれに当たります。
重要なのは、表現とリソースは別物であり、表現の形式（JSON、XML など）は交換可能であるという点です。

3. 自己記述的なメッセージ

自己記述的とは、クライアントが外部の仕様書や状態を保持せずとも、そのメッセージ単体で処理や意味を理解できることを意味します。これによりサーバ側の変更に対してもクライアントが柔軟に対応しやすくなります。

たとえば、HTTP ヘッダーに含まれる Content-Type や Authorization などは、リクエストやレスポンスがどのように処理されるべきかを記述するための情報であり、自己記述性を実現するために不可欠な要素です。各メッセージには、その意味を解釈するための必要な情報が含まれていなければなりません。

4. ハイパーメディアを状態遷移の手段とする（HATEOAS）

クライアントが次に何をすべきか、どこにアクセスすべきかを、サーバーから提供されるリンクなどのハイパーメディアによって誘導するという考え方です。ユーザーが今できる操作をリンクとしてレスポンスに含める設計は、この HATEOAS の実践例となります。

このうち最後の「ハイパーメディアによる制御（HATEOAS）」は特に難解で、現場であまり使われていない要素でもあります。

実例に見る REST 的な設計の価値

筆者がかつて開発したワークフローシステムでは、REST の考え方を部分的に応用しました。あるドキュメントを表示したとき、ユーザーのロールとドキュメントの状態に応じて、そのユーザーが可能な操作（たとえば「承認」「却下」など）をリンクとしてレスポンスに含めて返す仕組みです。

これにより、クライアント側は操作の可否を判断する必要がなくなり、表示されるボタンはサーバーからのレスポンスに基づいて決まります。

これは完全な HATEOAS 実装ではありませんが、REST の設計思想に含まれる「状態遷移をサーバーが導く」という考え方を取り入れたものであり、結果として：

  • セキュリティの強化
  • フロントエンドの単純化
  • API の保守性向上

といった効果が得られました。

REST と HTTP API を見分ける視点

以下の視点から、自身の API が REST の設計原則に沿っているかを確認できます：

  • URI はリソースの識別子として機能しているか？
  • 各リクエスト／レスポンスは自己記述的か？
  • 状態遷移の手段はハードコードされたルールではなく、サーバーが示しているか？
  • クライアントは操作を URI ではなくリンクから知ることができるか？

もし、これらの問いに十分に答えられない場合、それは REST ではなく、単なる HTTP API である可能性があります。

さらに REST を活かすには？

この文書では、REST と HTTP API の違いを中心に、REST の設計原則がどのように API 設計に影響を与えるかを見てきました。ここからは、実際の開発現場で REST の思想をより効果的に活用するためのヒントをいくつか紹介します。

状態とロールに応じた操作制御

業務アプリケーションでは、リソースの状態とユーザーのロールの組み合わせによって許可される操作が変化するケースが多くあります。これをサーバー側で判断し、可能な操作をリンクやアクションとして明示的に返すことで、クライアント実装を簡素化でき、セキュリティも高まります。

状態遷移の設計と REST の親和性

REST の設計は、リソースが持つ状態とその状態の遷移を明確に表現することに向いています。状態遷移のルールをステートマシンのように定義し、それに応じたリンクやアクションを提供することで、API の意図がより明確になります。

リンクベース設計の導入

サーバーが「今できる操作」をリンクとして返す設計は、柔軟な UI 実装にもつながります。ユーザーごとに異なる操作権限や状態に対応しやすくなり、将来的な拡張にも強い設計となります。JSON:API や HAL などの仕様もこの設計を後押ししてくれるでしょう。

設計段階で REST の原則を取り入れる

API 設計の初期段階から、REST の原則（リソースの識別、表現、操作、遷移）を意識することで、後々の拡張や保守が容易になります。機能ベースではなくリソースベースで考えることが、REST 的な設計の第一歩です。

他の技術との使い分けを意識する

GraphQL や gRPC のような技術も、特定の要件においては有力な選択肢となります。ただし、状態管理や疎結合を求められるシーンでは、REST の設計が引き続き有効である場面も多くあります。目的に応じて使い分ける視点を持つことが重要です。

おわりに

REST は単なる技術用語ではなく、Web システムを健全に保ち、拡張性・保守性・安全性を高めるための設計思想です。

HTTP API はその実装手段のひとつでしかなく、REST の本質を理解せずに API を設計してしまうと、思わぬ形で拡張性やセキュリティに問題が生じることがあります。

この文書を通じて、REST と HTTP API の違いを見極める力を身につけ、より良い API 設計につなげていただければ幸いです。
